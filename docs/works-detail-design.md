# Works 詳細ページ設計メモ

最終更新: 2026-08-14

## 目的

Works 一覧から遷移する作品詳細ページについて、現在のプロジェクト構成で実現可能なデータモデルと表示方針を記録する。

検討時に参照したワイヤーフレームは `/Users/saka/Downloads/Work Detail (Standalone).html`。この文書は実装手順ではなく、設計上の合意と保留事項を残すものである。合意内容に基づく初期実装は 2026-08-14 に完了した。

## 現状と実現性

- Astro の Content Collections で Work を管理している。
- `/works/[slug].astro` と `getStaticPaths()` で、公開対象の Work から詳細ページを静的生成している。
- Markdown と MDX の本文は `astro:content` の `render()` を通して同じ詳細ページに表示する。
- `embla-carousel` を詳細ページの手動ギャラリーにも利用している。
- 公式 MDX integration を導入し、Work コレクションは `.md` と `.mdx` の両方を読み込む。

## 合意した設計

### 公開 URL と slug

- Work は明示的な `slug` を持つ。
- slug は ASCII 小文字の kebab-case とする。
- slug は Work 間で一意とする。
- slug は保存場所やタイトルから独立した公開識別子として扱う。
- 公開後の slug は原則として変更しない。
- 将来やむを得ず変更する場合は、旧 URL からのリダイレクトを考慮する。

### 画像

- すべての Work は1枚以上の `images` を持つ。
- `images` の配列順をギャラリーの表示順とする。
- `images[0]` を代表画像とし、以下に利用する。
  - Works 一覧のカード画像
  - 詳細ページのギャラリー初期表示
  - OGP などの共有画像
- 各画像の `alt` は必須とする。
- 初期実装では画像キャプションを扱わない。必要になった場合にデータモデルと表示方法を追加検討する。
- 一覧カードは 4:3 の枠を基本とし、詳細ギャラリーでは画像全体を確認できる表示を基本とする。
- 将来、一覧専用画像が必要になった場合だけ、代表画像を上書きする仕組みを検討する。

### ギャラリー

- 詳細ページ上部に手動操作の画像ギャラリーを設ける。
- 自動再生は行わない。
- 複数画像の場合は、スワイプ、前後操作、キーボード操作、サムネイル選択を想定する。
- 画像が1枚だけの場合は、不要なサムネイル、矢印、カウンターを表示しない。
- サムネイル操作にはボタン要素を使用し、現在選択中の画像を支援技術にも伝える。
- 2枚目以降は遅延読み込みを基本とする。

### Markdown と MDX

- Work コレクション内で `.md` と `.mdx` を混在させる。
- 通常の作品紹介には `.md` を使用する。
- 動画などの専用コンポーネントが必要な作品だけ `.mdx` を使用する。
- 詳細ページ側はファイル形式を意識せず、同じ Content Collection のエントリとして本文を描画する。
- 本文の見出しは、ページタイトルの `h1` と競合しないよう `##` から始める。
- ギャラリーは完成品や主要スクリーンショット、本文中画像は制作過程・比較・補足説明という役割分担を基本とする。
- 本文中の通常画像には Markdown 標準構文 `![alt](./image.png)` を使用する。
- 本文画像は作品の Markdown または MDX と同じディレクトリを基本の保存場所とし、`src/content/works/` 以下のローカル画像として管理する。
- `public/` 以下の画像と生の `<img>` は Astro の画像最適化対象にならないため、本文画像には原則として使用しない。
- Astro のグローバル画像設定では `layout: "constrained"` と `responsiveStyles: true` を使用し、Markdown 構文の画像にも `srcset`、`sizes` とレスポンシブ表示を適用する。
- 既存の Works カードなど、`widths`、`sizes` と CSS を手動調整済みの `<Image>` は、必要に応じて `layout="none"` を指定してグローバルな自動レイアウト生成の対象外にする。
- `layout="none"` を指定した場合も、コンポーネントに明示した `widths` と `sizes` による既存の最適化は維持する。
- 初期実装では本文画像専用の MDX コンポーネントを用意しない。キャプションや特殊レイアウトが必要になった場合に限り追加を検討する。

### 動画埋め込み

- 動画の有無や URL は Work のスキーマおよび frontmatter に持たせない。
- 動画は MDX 本文中の、説明上自然な位置に配置する。
- ローカル動画は将来的にも対応対象としない。
- 初期対応プロバイダーは YouTube のみとする。
- MDX から利用する公開インターフェースは、共通の `VideoEmbed` コンポーネントとする。
- `VideoEmbed` は少なくとも `provider`、動画 ID、アクセシブルな `title` を受け取る。
- 任意の iframe URL や生の iframe HTML は受け取らず、埋め込み URL と属性はコンポーネント側で生成する。
- YouTube は自動再生せず、`youtube-nocookie.com` と iframe の遅延読み込みを基本とする。
- 共通コンポーネントは以下を統一する。
  - レスポンシブな表示枠
  - 余白とキャプション
  - アクセシビリティ属性
  - フォールバックリンク
  - 遅延読み込み
- 将来ニコニコ動画を追加できるよう、共通表示とプロバイダー固有の URL・属性生成を分離する。
- 初期段階では未実装のニコニコ動画を型や API に予約せず、追加時に対応プロバイダーとして明示的に拡張する。
- 未対応プロバイダーは暗黙に表示せず、ビルド時に検出できる設計を目指す。
- 動画数や第三者通信が問題になった場合は、クリック後に iframe を生成する方式へコンポーネント内部で拡張できるようにする。初期実装では通常の `loading="lazy"` で十分とする。

### 公開状態

`status` と `draft` は異なる軸として扱う。

#### `status: wip | released`

- 作品そのものの完成状態を表す。
- `wip` の作品も公開対象とする。
- WIP であっても制作内容を紹介する価値があるため、一覧と詳細ページに WIP バッジを表示して公開する。

#### `draft`

- 作品紹介記事の完成・公開状態を表す。
- `draft: true` は、作品が WIP か Released かにかかわらず公開しない。
- draft の紹介は不完全なため、一覧、Featured、詳細ルート、前後ナビゲーションから除外する。
- `draft` 省略時は公開扱いとする。
- 静的サイトでは非表示にするだけでなく、draft の詳細ページ自体を生成しない。

組み合わせごとの挙動は以下のとおり。

| 作品の状態 | 紹介記事 | 公開結果             |
| ---------- | -------- | -------------------- |
| WIP        | 完成     | WIP バッジ付きで公開 |
| Released   | 完成     | 通常公開             |
| WIP        | Draft    | 非公開               |
| Released   | Draft    | 非公開               |

### 前後ナビゲーション

- 公開日の新しい順を基準とする。
- 「前／次」では方向が曖昧なため、「新しい作品」「古い作品」と表示する。
- 同じ公開日の Work がある場合は slug で順序を安定させる。
- 最初と最後では、存在しない側のリンクを表示しない。
- ナビゲーションは循環させない。
- draft は除外し、公開中の WIP は含める。

### メタ情報

- `title`、`summary`、`kind`、`publishedAt`、`tags`、`links`、`collaboration` は現在の構造を利用できる。
- Development Work の `platforms` と `stacks` は通常タグへ混ぜず、詳細ページの専用メタ情報として扱う方向とする。
- 組織制作のクレジットは組織名のみ表示できれば十分とし、担当範囲や共同制作者の構造化表示は今回扱わない。
- `links` は0件を許可する。0件の場合は、リンク欄とリンク専用の区切りを表示しない。
- Work の外部リンクは別タブで開き、`target="_blank"` と適切な `rel` 属性を設定する。
- サイト内の外部リンク挙動には現状一貫していない箇所があるが、その統一は別タスクとして扱う。
- 公開日は年月日まで表示する。

### SEO と共有

- 詳細ページごとに title と description を設定する。
- 代表画像である `images[0]` を OGP 画像として利用する。
- canonical URL、OGP、SNS カード用メタデータを詳細ページで提供する方向とする。
- 共通 Layout は canonical URL、OGP、SNS カード用メタデータを受け取れるよう拡張済みである。

## ワイヤーフレームとの差分と扱い

- ワイヤーフレームには動画とギャラリーを排他的に切り替える表現があるが、実装では画像を全作品必須とし、動画は本文中の任意要素とする。
- ワイヤーフレームにはギャラリー配置を切り替える案があるが、作品データとしてレイアウト指定を持たせず、レスポンシブ UI 側で統一する方向とする。
- ワイヤーフレームには Footer があるが、今回の Works 詳細ページ実装では追加しない。共通 Footer はサイト全体の別タスクとして扱う。

## 今回の対象外・将来検討

- 共通 Footer の追加。
- サイト全体における外部リンクの別タブ表示の統一。
- 必要が生じた場合の、画像キャプションおよび本文画像専用 MDX コンポーネントの追加。
- 必要が生じた場合の、組織名以外の担当範囲や共同制作者の構造化表示。

これらは Works 詳細ページの初期実装には含めず、それぞれ必要になった時点で別途検討する。現時点で、詳細ページの基本構造に関する未解決のブロッカーはない。
